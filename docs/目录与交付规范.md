# 仓库目录与交付规范

## 1. 有效目录拓扑

```text
2026TI-kft/
├─ docs/                         当前系统权威文档
├─ tools/                        根级目录守卫与一键软件验收
├─ k230/                         视觉训练、部署与板端协议运行时
├─ mspm0/
│  ├─ MSPM0G3507_Project/
│  │  └─ MSPM0G3507_FreeRTOS/    比赛使用的两轮差速底盘固件
│  ├─ MSPM0G3507_M0_Base/        上游 Board B/旧拓扑参考，不参与比赛构建
│  ├─ tools/                     上游调试工具
│  └─ UPSTREAM.md                上游分支和导入基线
├─ stm32f4/balance_control/       比赛使用的滚球平衡主控固件
├─ SDM18/                        厂商资料快照，只读参考
├─ WHEELTEC MS42CG.../           步进电机厂商资料快照，只读参考
└─ H题_车载平衡滚球运动控制系统.pdf  原始赛题，只读基准
```

不移动 `SDM18/`、步进电机资料和 MSPM0 上游快照：其中包含厂商工程的相对路径、
预编译工具和历史说明，重排会降低可追溯性。它们不属于当前构建输入，也不允许在
其中放置本项目新增业务代码。

## 2. 代码所有权边界

| 层级 | 唯一职责 | 禁止事项 |
|---|---|---|
| K230 `runtime/` | 球视觉测量、像素到物理坐标、置信度和帧龄 | 直接产生步进脉冲或底盘 PWM |
| MSPM0 `Application/Algorithm/` | 无硬件依赖的 IMU、循迹和规划算法 | 访问 UART、GPIO、FreeRTOS |
| MSPM0 `Application/`/`Task/` | 组合算法、状态机、双轮目标和通信 | 绕过控制任务长期直接写电机 |
| STM32 `User/Bsp/` | HAL 外设薄适配 | 实现比赛状态机或控制律 |
| STM32 `User/Protocol/` | 帧、CRC、解析和有界发送 | 修改执行器或安全状态 |
| STM32 `User/App/` | 估计、平衡控制、安全和调度 | 暴露 HAL 句柄给纯控制核心 |
| `Core/`、`Drivers/` | CubeMX 与 ST 生成/供应代码 | 放置不可再生的业务逻辑 |

每个执行器只有一个正常控制写入者：MSPM0 电机由 5 ms 控制任务写入，STM32 STEP
由控制器经步进 BSP 写入。急停可以抢占，但不能形成第二套常规控制路径。

## 3. 配置归属

- 底盘机械尺寸、任务周期、IMU 安装矩阵/杆臂和默认循迹档位：
  `mspm0/.../Config/project_config.h`。
- 纯循迹自定义运行参数：整体构造 `app_line_follower_cfg_t` 后经校验接口原子切换。
- STM32 功能开关、超时和默认比赛动作：`stm32f4/balance_control/User/Config/user_config.h`。
- STM32 引脚、时钟、DMA、NVIC：`balance_control.ioc`，不要复制到 `user_config.h`。
- K230 相机和像素—毫米标定：部署配置或板端启动参数，不写死开发机绝对路径。

机械标定值必须携带固件提交号和日期。未经实车测量的默认值只能用于架空台架，
不能作为比赛验收参数。

## 4. 生成文件和依赖管理

- CubeMX 只允许重生成 `Core/`、`Drivers/` 和工程文件；生成后立即运行 STM32 三项
  结构检查，确认 `User/` 源文件仍被工程引用。
- TI SysConfig 以 `Config/empty.syscfg` 为源，生成文件变更必须与 `.syscfg` 同提交。
- 不提交虚拟环境、缓存、临时日志、Keil `Objects/Listings` 或本机用户配置。
- 已纳入的版本化 HEX、厂商示例构建物和资料快照属于历史输入，不用新规则批量
  改写；新交付产物应放到仓库外的 `artifacts/`，该目录默认忽略。
- 不增加嵌套 `.git`；MSPM0 上游以源码快照管理，更新流程见 `mspm0/UPSTREAM.md`。

## 5. 分支、提交与发布

1. 开始前确认 `git status -sb` 干净并 `git fetch origin`。
2. 只修改当前任务需要的权威代码/文档；供应商快照不做格式化。
3. 运行 `powershell -File tools\verify_all.ps1`，再执行完整 Keil 构建和实车分级验收。
4. 提交信息使用 `feat(scope):`、`fix(scope):`、`docs(scope):` 等明确前缀。
5. 推送前确认本地分支未落后；禁止用强制推送覆盖他人提交。
6. 交付记录至少包含：提交 SHA、三端固件/脚本版本、参数档、标定表、完整链接的
   Flash/RAM 占用、测试输出、实车最差误差、异常注入结果和已知限制。

## 6. 完成定义

“软件完成”要求目录守卫、全部主机测试、IOC/工程结构检查和 ARM 语法检查通过；
“固件完成”还要求 MSPM0 与 STM32 的目标工程完整编译链接；“赛题完成”必须再经过
接线、急停、静态阶跃、动态循迹、停车精度和扰动降级的实车记录。三者不可互相替代。
